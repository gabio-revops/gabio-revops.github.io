JavaScript Forms

Populate Hidden Form Field on Non-HubSpot Page

Captures UTM parameters, referrer, or any URL query string and populates a hidden field on an external form before submission to HubSpot. Essential for attribution tracking when you can't use HubSpot's native forms.
Use Case You're using Webflow, Wordpress, or custom forms but still want to track campaign attribution in HubSpot. This script reads URL parameters and injects them into hidden fields so they flow into HubSpot on form submit via the Forms API.
JavaScript 
// Get URL parameter by name
function getParam(name) {
  const params = new URLSearchParams(window.location.search);
  return params.get(name) || '';
}

// Populate hidden fields on page load
document.addEventListener('DOMContentLoaded', function() {
  // UTM parameters
  document.getElementById('utm_source').value = getParam('utm_source');
  document.getElementById('utm_medium').value = getParam('utm_medium');
  document.getElementById('utm_campaign').value = getParam('utm_campaign');
  
  // Referrer
  document.getElementById('referrer').value = document.referrer;
  
  // First page visited (store in sessionStorage)
  if (!sessionStorage.getItem('first_page')) {
    sessionStorage.setItem('first_page', window.location.href);
  }
  document.getElementById('first_page').value = sessionStorage.getItem('first_page');
});
Notes: Make sure your hidden input IDs match the field names expected by your HubSpot form. For HubSpot Forms API submissions, the field names must match your HubSpot property internal names exactly. Use sessionStorage for first-touch attribution so it persists across pages in the same session.
Workflow Playbooks Projects

RFP Pipeline with Go/No-Go Playbook and Auto-Created Response Project

A three-part HubSpot build for managing inbound RFPs: a dedicated pipeline that keeps cold RFPs out of the sales win rate, a Go/No-Go Playbook that captures qualifying answers as structured data and computes a recommendation, and a chained workflow setup that spins up a Project with templated tasks and date logic once the deal commits to responding.
Use Case You're tracking RFPs in a spreadsheet, your win rate is getting dragged down by deals you never had a real shot at, and there's no shared view of who's working on what. This pattern moves the entire process into HubSpot, captures the qualification logic as data instead of vibes, and gives the AE, manager, and PM a single source of truth for tasks and deadlines.

1. Pipeline Structure

Cold RFPs (found via BidPrime, procurement portals, or Google alerts with no prior relationship) live in a dedicated RFP pipeline so they don't drag down the sales-led win rate. Influenced RFPs (where an active deal triggers a competitive bid requirement) stay in the standard sales pipeline with a Procurement Method = RFP flag on the deal.

RFP pipeline stages:

  • RFP Announced: entry point for cold RFPs. Playbook completes here.
  • Proposal in Progress: committed to responding. Project is created.
  • Proposal Submitted: awaiting shortlist or demo invitation.
  • Interview Confirmed: shortlisted; demo or presentation scheduled.
  • Proposal Accepted: selected; may include BAFO pricing negotiation before contract.
  • Contracting: legal terms finalized. RFP submissions usually include pre-negotiated exceptions, so this stage often moves faster than in a standard deal.
  • Closed Won / Closed Lost: opt-outs are logged as Closed Lost with reason "Opted Out" so reporting captures pass-rate without inflating win rate.

2. Go/No-Go Playbook

A HubSpot Playbook ("RFP - Go/No-Go Assessment") attaches to deals at the RFP Announced stage. It applies only to cold RFPs; influenced RFPs skip the playbook since the decision to pursue is already made. All six questions are required, which guarantees clean data for the downstream score and recommendation.

  • Did we have prior contact or provide input to this RFP?
  • Is the RFP clearly written for a competitor?
  • Do we have more than 1 week to respond?
  • Is the budget above $10K?
  • Will this bring us into a new state or represent a top logo?
  • Can we meet product requirements (including roadmap)?

3. Playbook Score (Calculated Property)

A deal-level calculation tallies favorable answers, returning 0-6. Criterion 2 is inverted on purpose: a competitor-written RFP is a bad sign, so "No" earns the point.

HubSpot Calculation 
if([did_we_have_prior_contact_or_provide_input_to_this_rfp] = "Yes", 1, 0) +
if([is_the_rfp_clearly_written_for_a_competitor] = "No", 1, 0) +
if([do_we_have_more_than_1_week_to_respond] = "Yes", 1, 0) +
if([is_the_budget_above_10k] = "Yes", 1, 0) +
if([will_this_bring_us_into_a_new_state_or_represent_a_top_logo] = "Yes", 1, 0) +
if([can_we_meet_product_requirements_including_roadmap] = "Yes", 1, 0)

4. Recommendation Workflow

Triggers on Playbook Log completed for the Go/No-Go Assessment, OR when Playbook Score changes to any value greater than 0. Re-enrollment is on, so edits to any criterion re-evaluate the recommendation. Enrollment requires all six criteria properties to be known, which guarantees the workflow only fires once the playbook is genuinely complete.

Single branch with ordered conditions; stops at the first match. The workflow notifies the manager once the recommendation is set, but stage advancement stays manual so the manager or rep can override.

Decision Order 
1. New state or top logo = Yes               -> GO
2. Response time > 1 week = No               -> NO-GO (Insufficient response time)
3. Can meet product requirements = No        -> NO-GO (Cannot meet product requirements)
4. Budget > $10K = No AND Prior contact = No -> NO-GO (Budget under $10K and not influenced)
5. Playbook Score >= 4                       -> GO
6. Else                                      -> NO-GO (Failed to meet 4 of 6 criteria)

No-Go Reason is a dropdown that only populates when the recommendation is NO-GO. That way the reason is always tied to an actual decline and never sits orphaned on a deal that ended up advancing.

5. Project + Three Chained Workflows

Once a deal advances to Proposal in Progress (RFP pipeline) or 3 - Proposal Review (standard sales pipeline), a HubSpot Project is created and linked to the deal. The same automation runs from both pipelines so cold and influenced RFPs both benefit from the templated tasks and date logic.

The build is three single-responsibility workflows so each one fires off the record created by the previous step. This sidesteps the usual "newly-created record ID" lookup problem in HubSpot workflows, where you can't reference a record's ID in the same workflow that just created it.

Project-Level Date Properties

Four date properties live on the project. Three populate automatically; one is manual.

  • RFP Response Deadline: copied from the deal's RFP Deadline by Workflow 1.
  • RFP Q&A Deadline: manual entry. Q&A timing varies by RFP with no consistent offset from the response deadline, so it's left for the AE to enter when the schedule is known.
  • RFP Internal Review Deadline: calculated. [RFP Response Deadline] - (3 * 86400000). Three days before submission.
  • RFP Internal Debrief Deadline: calculated. [RFP Response Deadline] + (5 * 86400000). Five days after submission.

RFP Deadline is enforced as a required deal property whenever Procurement Method = RFP via conditional property logic. That guarantees Workflow 1 always has a date to copy forward, and that all downstream calculated dates resolve.

Workflow 1: Create Project

  • Trigger: Deal stage changes to Proposal in Progress (RFP pipeline) or 3 - Proposal Review (sales pipeline). Re-enroll off.
  • Enrollment: Procurement Method = RFP.
  • Action: Creates a project named "RFP Response - [Deal Name]" in the RFP Responses pipeline at the Planning stage. Owner = deal owner. Target due date copies from the deal's RFP Deadline. Associated to the enrolled deal and the deal's primary company.

Workflow 2: Create Tasks

  • Trigger: Project record created. Re-enroll off.
  • Enrollment: Project name starts with "RFP Response" AND Create date is Today. The Today guard prevents historical projects from getting a fresh round of tasks if the workflow is ever toggled off and back on.
  • Action: Eleven sequential Create Task steps from the RFP playbook template. Each task is assigned to the project owner (AE) except the win/loss debrief, which is assigned to the manager.
  • Token usage: The "Create Slack channel" task uses the City (Company) token so the reminder text dynamically populates with the actual city name, e.g., "Create Slack channel #rfp-austin".

Workflow 3: Set Task Dates

  • Trigger: Task records meeting custom conditions: status is none of Completed AND task title matches one of the four deadline-bearing tasks. Re-enroll off. The workflow only sets task due dates at task creation; it does not refire on later property changes.
  • Action: Single branch on Task Title routes each matching task to its corresponding date logic. Each route checks whether the relevant project-level deadline is known, pulls it via "Project: Most recently associated", and sets the task due date from that property. If the project date is missing, the task keeps its existing due date as a fallback.
  • Routing:
    • "Submit questions by Q&A deadline; join Q&A session" → RFP Q&A Deadline
    • "Submit to Manager for review (min. 2 days before deadline)" → RFP Internal Review Deadline
    • "Submit RFP (ideally 1 day early)" → RFP Response Deadline
    • "Log win/loss debrief notes in HubSpot" → RFP Internal Debrief Deadline
  • Date math gotcha: HubSpot date fields are stored as milliseconds, so any day offset in a calculated property must be expressed as days * 86400000. The bigger trap: task due dates are set once, at task creation. If the response deadline shifts mid-project, the project-level calculated dates recalc automatically, but the task dates do not. The AE has to update them by hand when a deadline moves.
Same pattern, other use cases: I've reused this stage-gated playbook + chained project-creation pattern for two adjacent processes.

Onboarding at Closed Won. A sales-to-CS handoff playbook fires at Closed Won and captures the context CS needs to onboard cleanly: champion vs. economic buyer, success criteria from the deal, integrations promised, contract terms that affect provisioning, known risks. A project spins up with the implementation tasks and dates derived from contract start.

Trial / pilot pipeline. A setup playbook captures everything needed to provision a trial org: data volume, seat count, sandbox vs. production, integrations to enable, success metric the prospect agreed to measure. A project templates the trial milestones (kickoff, mid-point check, final review) with dates derived from the trial start date.

The general recipe: a stage-gated playbook captures structured data, a calculated property plus workflow turns that data into a routing decision or status, and a chained project-creation workflow templates the work that follows. Swap the questions, swap the tasks, keep the chain.
